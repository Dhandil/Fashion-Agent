# Fashion-Agent 产品定位与范围

## 1. 文档信息

- 项目名称：Fashion-Agent
- 产品类型：AI 个人穿搭与衣橱助手
- 文档状态：已确认
- 当前版本：0.1
- 更新日期：2026-07-30

本文档用于确定 Fashion-Agent 的产品定位、目标用户、核心能力、业务边界和开发优先级。

后续需求设计、数据库建模、Agent 工作流和工具开发，都应以本文档为产品范围基准。

---

## 2. 产品定位

Fashion-Agent 是面向年轻用户的 AI 个人穿搭决策助手。

它根据用户的穿搭场景、天气、风格偏好、身材尺码、已有衣橱和预算，生成适合用户且能够实际执行的穿搭方案。

Fashion-Agent 优先帮助用户使用已有衣物完成搭配。只有当现有衣橱无法满足需求，或者用户明确提出购买需求时，才调用外部商品搜索能力，帮助用户发现和比较适合的商品。

Fashion-Agent 不作为电商交易平台，不直接执行购买、支付、下单、物流或售后操作。

### 2.1 一句话定位

> 先帮用户决定怎么穿，再判断是否需要买。

### 2.2 核心价值

> 让用户用更少的决策时间和更合理的消费，获得适合自己、符合场景并且能够真正执行的穿搭方案。

### 2.3 产品原则

1. 穿搭方案优先，商品推荐其次。
2. 优先使用用户已有衣物，减少不必要购买。
3. 推荐必须考虑用户、场景和现实约束。
4. 商品信息必须来自真实工具或外部数据源。
5. 不虚构商品、价格、库存、尺码和购买链接。
6. 对推荐理由进行简洁、可理解的解释。
7. 用户始终保留最终选择权。
8. 用户隐私和敏感信息遵循最小化收集原则。

---

## 3. 目标用户

Fashion-Agent 主要面向有以下需求的年轻用户：

- 缺少系统穿搭知识。
- 每天花费较多时间决定穿什么。
- 面对特定场景时不知道如何搭配。
- 衣服不少，但不知道如何组合。
- 容易重复购买相似衣物。
- 希望建立适合自己的稳定风格。
- 希望在有限预算内改善穿搭。
- 购买衣服前希望得到理性建议。

产品不强制限定用户的性别、风格或服装品类。

系统应允许用户主动描述自己的身份、身体特点和表达偏好，不应仅根据姓名、头像或历史信息擅自推断敏感属性。

---

## 4. 用户核心任务

Fashion-Agent 解决的核心任务是：

> 在具体场景和现实约束下，帮助用户完成一套适合自己的穿搭。

一项完整穿搭决策可能包含以下输入：

- 穿搭场景
- 日期和天气
- 所在城市
- 季节
- 风格偏好
- 正式程度
- 用户已有衣物
- 身材与尺码
- 颜色偏好
- 不喜欢的材质
- 可接受预算
- 是否愿意购买新单品

系统不要求用户一次提供所有信息。

Agent 应判断当前缺少哪些关键信息，并只提出必要、简短的补充问题。

## 5. 标准用户流程

### 5.1 使用已有衣橱完成穿搭

```text
用户提出穿搭需求
→ Agent 分析场景和限制
→ 查询用户风格档案
→ 查询用户已有衣橱
→ 检索服装知识
→ 生成一套或多套搭配
→ 解释搭配理由
→ 用户选择或继续调整
```

### 5.2 衣橱存在缺口时推荐商品

```text
用户提出穿搭需求
→ Agent 生成理想搭配结构
→ 查询用户已有衣橱
→ 判断缺少的关键单品
→ 询问用户是否愿意购买
→ 调用外部商品搜索工具
→ 比较商品与搭配需求
→ 返回商品信息和原始购买链接
→ 用户前往来源平台完成交易
```

### 5.3 用户明确提出购物需求

```text
用户明确要求购买某类衣服
→ Agent 收集品类、场景、风格、尺码和预算
→ 调用商品搜索工具
→ 获取真实商品数据
→ 结合穿搭知识进行筛选
→ 返回候选商品及推荐理由
→ 用户前往外部平台购买
```

## 6. 核心输出

Fashion-Agent 输出的重点是完整穿搭方案，而不是商品列表。

一份标准穿搭方案应尽量包含：

- 搭配名称或风格概述
- 适用场景
- 上装
- 下装
- 外套
- 鞋履
- 配饰
- 推荐理由
- 颜色关系
- 面料和天气适用性
- 已有衣物
- 缺少单品
- 可替换方案
- 注意事项
- 商品来源与链接（仅在需要购物时）

示例：

```text
方案：清爽的夏季通勤穿搭

上装：
已有的浅蓝色亚麻衬衫

下装：
已有的深灰色直筒西裤

鞋履：
黑色乐福鞋

搭配理由：
浅蓝和深灰保持专业感，同时不会显得过于沉重。
亚麻面料适合炎热天气，但需要注意自然褶皱。

衣橱缺口：
如果你目前没有黑色乐福鞋，可以继续使用白色简洁运动鞋，
或者让我帮你搜索预算范围内的乐福鞋。
```

## 7. 功能优先级

### 7.1 P0：核心 MVP

P0 用于形成第一个可用的穿搭闭环。

- 多轮穿搭对话
- 场景需求理解
- 季节和天气条件理解
- 风格、颜色、预算等约束提取
- 必要信息补充询问
- 通用穿搭方案生成
- 服装知识 RAG
- 面料和护理建议
- 对话短期记忆
- 商品搜索工具
- 商品价格和库存真实性约束
- 没有商品结果时如实返回
- 禁止自动购买和支付

### 7.2 P1：个人化与衣橱

- 用户穿搭档案
- 风格偏好
- 常用尺码
- 喜欢和不喜欢的颜色
- 不喜欢或过敏的材质
- 数字衣橱
- 衣物新增、修改和删除
- 根据已有衣物生成搭配
- 保存搭配方案
- 用户反馈
- 根据反馈调整后续推荐
- 衣橱缺口分析

### 7.3 P2：外部能力

- 实时天气工具
- 品牌或电商商品 API
- MCP 商品服务
- 多平台商品比较
- 商品价格和库存实时确认
- 图片识别衣物
- 衣橱图片录入
- 尺码建议
- 商品收藏
- 搭配日历
- Multi-Agent

### 7.4 当前不做

- 自动下单
- 自动支付
- 物流管理
- 售后处理
- 自营商城
- 时尚社交社区
- 服装生产和供应链管理
- 专业服装设计
- 复杂虚拟试衣
- 未授权网页的大规模商品抓取

## 8. 购物能力边界

购物是 Fashion-Agent 的辅助能力，用于补全穿搭需求，而不是产品的唯一目标。

### 8.1 允许的购物行为

- 理解购买需求
- 查询真实商品
- 按预算、品类和库存过滤
- 比较商品
- 解释商品为什么适合用户
- 提供商品来源平台
- 提供原始商品链接
- 推荐前重新确认价格和库存

### 8.2 禁止的购物行为

- 虚构商品
- 虚构价格或库存
- 将知识库内容当作真实商品
- 未经用户确认自动购买
- 保存支付密码
- 代替用户完成支付
- 承诺外部平台的价格、库存或售后
- 将过期缓存描述为实时数据

### 8.3 商品来源

正式环境中的商品数据优先来自：

1. 品牌或商家的官方 API
2. 电商开放平台 API
3. 联盟营销 API
4. 企业内部商品服务
5. 已授权的 MCP Server
6. 商家提供的结构化数据文件

`data/samples/products.json` 只用于本地开发和测试，不能被描述为生产环境的真实商品数据。

## 9. 核心领域模型

### 9.1 StyleProfile

保存用户长期穿搭偏好，例如：

- 用户 ID
- 常穿尺码
- 风格偏好
- 颜色偏好
- 不喜欢的颜色
- 材质偏好
- 不适合或过敏的材质
- 常见穿搭场景
- 常用预算范围

### 9.2 WardrobeItem

表示用户已经拥有的一件衣物，例如：

- 衣物 ID
- 用户 ID
- 名称
- 品类
- 颜色
- 材质
- 尺码
- 风格标签
- 适用季节
- 适用场景
- 图片
- 当前状态

### 9.3 Outfit

表示一套完整穿搭方案，例如：

- 搭配 ID
- 用户 ID
- 搭配名称
- 场景
- 风格
- 季节
- 推荐理由
- 创建时间
- 是否收藏

### 9.4 OutfitItem

表示一套搭配中包含的单品，例如：

- 搭配 ID
- 衣物 ID 或外部商品 ID
- 单品角色
- 是否来自用户衣橱
- 是否为待购买商品

### 9.5 Product

表示来自外部商品平台的候选商品，例如：

- 商品 ID
- 来源平台
- 外部商品 ID
- 名称
- 品类
- 品牌
- 价格
- 币种
- 颜色
- 尺码
- 库存
- 商品链接
- 最近同步时间
- 最近价格确认时间

`Product` 是辅助领域对象，不是系统最核心的数据对象。

## 10. 数据存储职责

### PostgreSQL

保存结构化、需要长期保留的数据：

- 用户穿搭档案
- 用户衣橱
- 搭配方案
- 搭配与衣物关系
- 用户反馈
- 收藏记录
- 外部商品缓存

### Redis

保存短期和高频访问的数据：

- 对话状态
- 临时 Agent 状态
- 会话过期时间
- 常用查询缓存
- 限流信息

### Chroma

保存需要语义检索的非结构化知识：

- 面料知识
- 颜色搭配知识
- 版型知识
- 穿搭原则
- 季节建议
- 衣物护理知识

### 外部 API 或 MCP

提供动态业务数据：

- 商品搜索
- 商品详情
- 实时价格
- 实时库存
- 天气
- 其他授权平台数据

## 11. Agent 逻辑

Fashion-Agent 的主工作流应逐步演进为：

```text
START
→ 分析用户需求
→ 判断信息是否充分
→ 必要时询问补充信息
→ 查询用户档案
→ 查询用户衣橱
→ 检索穿搭知识
→ 生成初步穿搭方案
→ 判断是否存在衣橱缺口
→ 按需调用商品搜索
→ 生成最终穿搭方案
→ END
```

商品工具不应在每次对话中默认调用。

只有满足以下条件之一时才调用：

- 用户明确要求购买或搜索商品。
- 用户同意为衣橱缺口购买新单品。
- 用户要求比较具体商品。
- 穿搭方案需要真实商品信息才能完成。

## 12. 未来 Multi-Agent 规划

当单 Agent 工作流稳定后，可以拆分为：

```text
Fashion Supervisor
├── Profile Agent
│   └── 管理用户偏好和尺码
├── Wardrobe Agent
│   └── 查询和管理用户衣橱
├── Styling Agent
│   └── 生成完整穿搭方案
├── Knowledge Agent
│   └── 检索服装知识
└── Shopping Agent
    └── 查询和比较外部商品
```

Multi-Agent 不是 MVP 的前置条件。

在单 Agent 的状态、工具和错误处理稳定以前，不提前增加多 Agent 调度复杂度。

---

## 13. 隐私与安全

Fashion-Agent 可能处理尺码、身体特征和消费偏好，因此必须遵循以下原则：

- 只收集实现功能所必需的信息。
- 不强迫用户提供性别、身高或体重。
- 不根据非必要信息推断敏感属性。
- 用户可以查看、修改和删除个人资料。
- API Key、密码和 Token 不进入数据库或 Git。
- 支付信息不由 Fashion-Agent 保存。
- 日志中不输出完整敏感数据。
- 商品推荐不能替代用户的最终判断。

## 14. MVP 验收标准

Fashion-Agent 的第一个核心版本至少应做到：

1. 用户可以用自然语言描述一个穿搭场景。
2. Agent 能识别场景、季节、风格和预算等约束。
3. 缺少关键信息时，Agent 会提出必要问题。
4. Agent 能利用知识库解释搭配和面料选择。
5. Agent 能生成结构清晰的一套穿搭方案。
6. 用户明确购物时，Agent 能调用真实商品工具。
7. 商品工具没有结果时，Agent 不虚构商品。
8. API 能保持同一 `conversation_id` 下的多轮上下文。
9. 系统不会自动下单或支付。
10. 核心模块具有单元测试和集成测试。

当前项目已经实现：

- FastAPI 聊天接口
- LangGraph 基础工作流
- DeepSeek/OpenAI 兼容模型
- 对话短期 Memory
- Chroma 服装知识 RAG
- Tool Registry
- 商品搜索工具
- JSON 样例商品仓库
- PostgreSQL 异步基础设施
- SQLAlchemy 商品模型

当前 `shopping` 相关模块名称来自项目早期的购物助手定位。

后续会逐步调整为以 Fashion 和 Styling 为中心的命名，但不会一次性重命名全部文件，以避免无意义的大规模改动。

现有商品搜索代码继续保留，并重新定义为 Fashion-Agent 的辅助购物能力。

## 16. 已确认的产品决策

1. Fashion-Agent 不是电商平台。
2. Fashion-Agent 不是单纯的商品搜索机器人。
3. Fashion-Agent 的核心产物是穿搭方案。
4. 用户已有衣橱优先于购买新商品。
5. 商品搜索用于补全衣橱缺口或响应明确购物需求。
6. 商品交易在外部来源平台完成。
7. PostgreSQL 的核心数据将包括用户档案、衣橱和搭配。
8. Chroma 负责非结构化服装知识。
9. Redis 负责短期会话和缓存。
10. 外部商品和天气数据通过 API、Tool 或 MCP 接入。

# Fashion-Agent 开发路线图

## 1. 文档目的

本文档记录 Fashion-Agent 的当前进度、开发顺序、阶段目标和近期任务。

- 产品定位与业务边界以 [产品定位与范围](./product_scope.md) 为准。
- 可测试需求以 [需求规格](./requirements.md) 为准。
- 技术边界和模块职责以 [系统架构](./architecture.md) 为准。

路线图会随着项目推进持续更新，但不得改变以下核心定位：

> Fashion-Agent 是个人穿搭与衣橱助手。它先帮助用户决定怎么穿，再判断是否需要购买。

---

## 2. 产品主线

Fashion-Agent 的核心业务闭环是：

```text
理解用户的穿搭需求
→ 读取用户风格档案和衣橱
→ 排除当前不可用的衣物
→ 结合场景、风格和服装知识
→ 生成完整且可执行的 Outfit
→ 解释搭配理由并允许用户调整
→ 只有缺少关键单品时才建议购物
```

开发工作应优先服务这条主线，避免项目演变为只有数据库 CRUD 的后台系统，或者以商品搜索为主的购物机器人。

## 4. 已完成阶段：衣橱驱动的穿搭 MVP

### 4.1 阶段目标

让 Agent 能读取当前用户的真实衣橱，并优先使用已有衣物生成一套完整 Outfit。

本阶段完成后，项目应第一次形成真正符合产品定位的纵向业务闭环：

```text
用户提出穿搭需求
→ Agent 查询该用户的可用衣物
→ Agent 检索相关服装知识
→ Agent 生成基于已有衣物的 Outfit
→ Agent 说明搭配理由和衣橱缺口
```

### 4.2 实施顺序

1. [已完成] 创建当前用户衣橱查询能力。
2. [已完成] 将衣橱查询封装为 Agent Tool。
3. [已完成] 在请求级数据库 Session 中创建衣橱 Tool。
4. [已完成] 将请求级 Tool 安全地注入 LangGraph，避免缓存数据库 Session。
5. [已完成] 让 Agent 优先根据查询到的衣物生成 Outfit。
6. [已完成] 为 Outfit 回复定义稳定的结构。
7. [已完成] 增加 Tool、Graph、API 和真实数据库链路测试。

### 4.3 Outfit 最小输出

一份 Outfit 应尽量包含：

- 搭配名称
- 适用场景
- 上装
- 下装
- 鞋履
- 按需提供的外套和配饰
- 搭配理由
- 颜色和面料关系
- 已使用的衣橱单品
- 可替换单品
- 衣橱缺口

不能为了填满结构而虚构用户拥有的衣物。

### 4.4 衣物状态决策

当前只保留两种业务状态：

- `available`：当前可以参与穿搭推荐
- `unavailable`：当前不参与穿搭推荐

待洗、清洗中、晾晒中或暂时找不到，对当前推荐结果的影响相同，因此现阶段不拆分成多个状态。

如果以后确实需要洗衣提醒，可以在不改变可用性判断的前提下增加不可用原因。

### 4.5 阶段验收标准

1. Agent 只能读取当前用户的衣橱。
2. 用户 ID 不能由 LLM 或请求正文指定。
3. 不可用衣物不能进入推荐候选。
4. 有合适衣物时优先使用已有衣物。
5. 没有合适衣物时如实说明缺口，不虚构衣物。
6. 未获得用户购物意愿时，不自动搜索商品。
7. 单元测试和集成测试通过。

### 5.4 后续里程碑：上下文、记忆与基础可观测性

上下文、记忆和可观测性解决的是不同问题：

| 能力 | 作用 | 生命周期 |
|---|---|---|
| 上下文 Context | 决定本次模型调用实际看到什么 | 单次模型调用 |
| 短期记忆 | 保留同一会话中的消息和工作流状态 | 一个 `conversation_id` |
| 长期记忆 | 保存跨会话使用的已确认用户事实 | 用户明确修改或删除前 |
| Observability | 让开发者理解请求如何执行及为何失败 | 按日志和追踪策略保留 |

这些能力不能等到项目最后一次性补齐。知识库扩大后，Prompt 长度、来源
冲突和调试难度都会增加，因此应在复杂 Agent 工作流之前建立基础规则。

#### 5.4.1 上下文管理

建立统一的上下文包，明确各部分来源和优先级：

```text
Context Package
├── 当前用户请求
├── 当前轮消息
├── 对话滚动摘要
├── 上一套 Outfit
├── Style Profile
├── 当前轮衣橱和其他工具事实
├── 当前天气
├── 近期 Outfit 与反馈
└── RAG 知识片段
```

上下文优先级：

1. P0：系统规则和当前用户明确要求
2. P1：当前轮工具事实、天气和衣橱
3. P2：Style Profile 和上一套 Outfit
4. P3：对话摘要、近期 Outfit 和历史反馈
5. P4：RAG 参考知识

需要完成：

- [已完成] 第一版统一 Context Package 和可配置总字符预算
- [已完成] 按 P1 到 P4 处理当前事实、明确记忆、历史记忆和 RAG
- [已完成] 对正文去重，并在预算不足时截断文本或整项省略结构化 JSON
- [已完成] Chat 与结构化 Outfit 生成共用相同的上下文边界规则
- [已完成] 记录输入、选中、重复、省略和截断计数，不记录上下文正文
- 后续增加模型相关 Token 预算和各类上下文独立预算
- 只保留最近有限轮原始消息，更早内容压缩为滚动摘要
- RAG 片段数量、单片段长度和总长度限制
- 每类上下文的来源、版本和更新时间
- 上下文超限、内容为空和来源冲突测试

对话摘要只帮助理解连续意图，不能作为商品 ID、价格、库存、天气或衣橱
状态的权威来源；这些动态事实必须重新查询对应 Provider、Repository 或
Tool。

#### 5.4.2 短期记忆

当前 `InMemorySaver` 继续用于本地开发。生产目标是可配置的异步 Redis
Checkpointer：

```text
development
→ InMemorySaver

production
→ Redis Checkpointer
```

短期记忆可以保存：

- 多轮消息和滚动摘要
- 上一套结构化 Outfit
- 待补充的问题和需求分析状态
- LangGraph 中断与恢复位置

需要增加：

- `user_id + conversation_id` 会话隔离
- 最后活动时间和自动刷新 TTL
- 最大消息数、最大状态大小和检查点数量限制
- 查询、删除和显式结束会话
- 用户删除账户时清理会话数据
- 多 API 实例共享
- Redis 不可用时的明确降级和健康检查

Redis Checkpointer 需要增加依赖和 Docker 服务，实施前必须经过用户同意。

#### 5.4.3 长期记忆

PostgreSQL 中已有的 Style Profile、衣橱、已保存 Outfit、收藏和反馈就是
当前的长期记忆，不再为了目录完整复制一套存储。

长期记忆只接受：

- 用户明确提供的事实
- 用户主动保存、收藏或反馈的结果
- 系统生成候选后由用户明确确认的偏好

以下内容不能自动写入长期记忆：

- 当前天气和单次场景需求
- 原始工具结果和 RAG 片段
- LLM 根据一次对话推断的风格、身材或偏好
- 未经确认的聊天摘要和偏好候选

后续补充长期记忆的来源、证据、创建时间、最近确认时间、冲突检测、过期、
用户修改和删除能力。暂不把全部原始聊天记录自动写入用户向量记忆库。

#### 5.4.4 基础可观测性

先建立不会泄露用户数据的基础观测，再选择外部平台。

结构化日志应包含：

- `request_id`、`conversation_id` 和匿名化用户标识
- Graph 节点、工具名称、执行状态和错误类型
- API、LLM、RAG、Tool 和数据库耗时
- 检索片段数、Outfit 是否生成以及是否发生降级

基础指标包括：

- API 请求量、延迟和错误率
- LLM 延迟、Token 使用量和失败率
- Tool 调用量、失败率和超时率
- RAG 检索延迟、空结果率和来源数量
- Outfit 生成、校验和修正成功率
- PostgreSQL、Redis、Chroma 和天气 Provider 延迟

链路追踪应能还原：

```text
FastAPI Request
→ LangGraph
→ Profile / Recent Outfit / Feedback
→ RAG
→ LLM
→ Tools
→ Outfit Generation
→ Response
```

日志和 Trace 默认不得记录 API Key、密码、完整 Prompt、完整用户消息、
Style Profile 或衣橱隐私数据。需要定义脱敏、采样、保留和用户删除策略。

实施顺序：

1. [已完成] 在知识库阶段增加第一版上下文预算、来源信息和基础耗时日志。
2. [已完成] 使用标准库完成 `request_id` 和基础结构化事件，不增加外部依赖。
   HTTP 响应通过 `X-Request-ID` 回传追踪 ID，LangGraph metadata 继承同一 ID。
3. 结构化需求分析完成后增加滚动摘要。
4. 经用户同意后接入 Redis Checkpointer、TTL 和会话生命周期。
5. 经用户同意后使用 OpenTelemetry，并把 LangSmith 保持为可选开发工具。

### 5.5 已完成第一版：结构化需求分析

正式知识库能够提供稳定依据后，为 Agent 增加明确的需求分析结果，例如：

```text
场景：通勤
日期：明天
地点：上海
正式程度：商务休闲
风格：简约
颜色偏好：浅色
衣橱优先：是
购物意愿：无
信息是否充分：否
缺失信息：鞋履要求
```

LangGraph 根据分析结果执行确定性分支：

```text
信息不足
→ 只追问必要问题

信息充分
→ 读取档案、查询衣橱和检索知识

用户明确购物或确认衣橱缺口
→ 才允许查询商品
```

这一阶段重点减少无意义追问、错误工具调用和信息不足时的武断推荐。

第一版已完成：

- [已完成] 定义意图、场景、日期、地点、正式程度、风格、颜色、衣橱优先、
  天气需要、购物意愿、充分度和缺失字段的结构化模型
- [已完成] 使用独立结构化节点分析当前轮请求，并在供应商失败时保守降级
- [已完成] 缺失字段限制为标准枚举，单轮最多追问三个必要字段
- [已完成] 信息不足时直接生成确定性追问，不读取 RAG、用户档案或业务工具
- [已完成] 通用知识问题走轻量 Retriever 链路，个性化请求才加载用户上下文
- [已完成] 只有当前用户原文明示购物时才允许 `search_products`
- [已完成] 拒绝越权工具调用并限制同一轮重复拒绝，避免工具循环
- [已完成] 每轮开始清除上一轮派生上下文，避免轻量路由返回旧知识来源

后续需要使用真实对话问题集评估意图、充分度和缺失字段准确率，并根据误判
调整 Prompt 与确定性规则。

### 5.6 已完成第一版：Outfit 可执行性检查

结构化 Outfit 生成后增加独立检查，而不是把模型第一次输出直接视为最终
方案。检查内容包括：

- 不可用衣物是否进入方案
- 天气和温度是否适合
- 场景正式程度是否匹配
- 颜色是否存在明显冲突
- 上装、下装和鞋履等核心角色是否完整
- 洗涤、晾晒或护理限制是否影响当天使用
- 衣橱和商品来源 ID 是否真实有效
- 是否违反用户明确避免的偏好

检查失败时只允许在真实数据边界内修正一次；仍无法通过时返回明确限制，
不能用虚构单品填满 Outfit。

第一版已完成：

- [已完成] 在结构化 Outfit 生成后增加独立确定性检查节点
- [已完成] 校验衣橱和商品来源 ID 是否来自当前轮真实工具结果
- [已完成] 拒绝不可用衣橱单品、无库存商品和重复真实单品引用
- [已完成] 完整穿搭请求校验上装、下装或连体装，以及鞋履等核心角色
- [已完成] 校验推荐场景与用户当前明确场景是否一致
- [已完成] 识别高温厚重保暖单品等高置信度天气冲突
- [已完成] 把低温保暖不足和降水防护不足作为非阻断警告
- [已完成] 错误方案不进入 API 的 `outfit`，问题通过 `outfit_issues` 返回
- [已完成] 可执行性事件只记录问题代码和数量，不记录衣橱或用户正文

受限修正闭环已完成：

- [已完成] 首次出现阻断错误时进入修正节点，不立即把失败方案返回给用户
- [已完成] 修正节点只读取当前轮结构化需求、衣橱、商品和天气事实
- [已完成] 修正结果重新执行同一套确定性检查
- [已完成] 修正失败或第二次检查仍失败时终止，不形成模型循环
- [已完成] 增加完整图测试，验证“生成、检查、修正、再检查”的真实执行顺序

护理可用性、颜色明显冲突和用户明确禁忌仍属于后续规则扩展，需先建立可复现
案例，避免凭主观规则过度阻断可用方案。

护理可用性的第一步已完成：

- [已完成] 继续使用 `available` / `unavailable` 两种状态，不把待洗、清洗中、
  未干和损坏拆成更多枚举
- [已完成] 衣橱搜索只返回 `available`，生成和修正上下文再次执行候选过滤
- [已完成] 高温时排除厚羊毛、羽绒、加绒等高置信度冲突候选
- [已完成] 完整原始工具事实仍由最终可执行性检查使用，不降低真实性标准

### 5.7 后续阶段：降低衣橱录入成本

衣橱是产品核心，但完全手工录入会限制真实使用。计划支持：

- 上传衣物照片
- 视觉模型识别品类、颜色、图案和可能材质
- 用户确认或修正识别结果
- 确认后写入衣橱
- 图片地址与结构化衣物记录关联

模型识别结果属于候选信息，未经用户确认不能成为永久衣橱事实。

### 5.8 后续阶段：真实用户界面

在核心穿搭质量稳定后，建设：

- 对话页面
- 衣橱管理和图片上传
- Outfit 卡片、收藏和反馈
- Style Profile 管理
- 天气与场景输入
- “换一件”“更正式”等局部调整操作

界面应围绕“今天怎么穿”和“用已有衣物完成搭配”设计，而不是围绕商品
列表设计。

### 5.9 后续阶段：辅助购物

购物能力只用于补全衣橱缺口，或者响应用户明确提出的购物需求：

```text
生成 Outfit
→ 发现缺少关键单品
→ 向用户说明缺口
→ 用户确认想购买
→ 查询真实商品平台
```

计划内容：

- 购物意愿确认
- 外部商品平台 API 或 MCP
- 商品字段标准化
- 按预算、尺码、颜色和库存过滤
- 商品来源与原始链接
- 推荐前重新确认动态价格和库存

Fashion-Agent 不负责下单、支付、物流和售后。

### 5.10 后续阶段：企业级完善

核心单 Agent 产品闭环稳定后，再完善：

- JWT 或 OAuth 真实身份认证
- API、PostgreSQL、Redis 的完整 Docker Compose
- Redis 高可用、容量、备份和故障恢复
- OpenTelemetry Collector 与生产观测后端
- 限流、超时、重试和熔断
- CI 自动测试和代码质量检查
- 生产环境 Secret 管理
- MCP Client 和 MCP Server
- 性能、安全和故障恢复测试

只有单 Agent 工作流和评估体系稳定后，才评估拆分：

```text
Fashion Supervisor
├── Profile Agent
├── Wardrobe Agent
├── Styling Agent
├── Knowledge Agent
└── Shopping Agent
```

Multi-Agent 是扩展方案，不是当前 MVP 的前置条件。

## 6. 数据技术的职责

数据库相关计划仍然需要保留，但应围绕业务能力逐步实施。

| 技术 | 主要职责 |
|---|---|
| PostgreSQL | 用户档案、衣橱、Outfit、反馈和外部商品缓存 |
| Redis | 短期会话、临时 Agent 状态、缓存和限流 |
| Chroma | 面料、颜色、版型、场景和护理等服装知识 |
| 外部 API/MCP | 实时天气、商品、价格和库存 |

实施原则：

> Agent 当前需要什么数据能力，就优先完善对应的数据接口；不为了表结构完整而提前开发暂时没有消费者的功能。

# Fashion-Agent 开发路线图

## 1. 文档目的

本文档记录 Fashion-Agent 的当前进度、开发顺序、阶段目标和近期任务。

- 产品定位与业务边界以 [产品定位与范围](./product_scope.md) 为准。
- 可测试需求以 [需求规格](./requirements.md) 为准。
- 技术边界和模块职责以 [系统架构](./architecture.md) 为准。

路线图会随着项目推进持续更新，但不得改变以下核心定位：

> Fashion-Agent 是个人穿搭与衣橱助手。它先帮助用户决定怎么穿，再判断是否需要购买。

---

## 2. 产品主线

Fashion-Agent 的核心业务闭环是：

```text
理解用户的穿搭需求
→ 读取用户风格档案和衣橱
→ 排除当前不可用的衣物
→ 结合场景、风格和服装知识
→ 生成完整且可执行的 Outfit
→ 解释搭配理由并允许用户调整
→ 只有缺少关键单品时才建议购物
```

开发工作应优先服务这条主线，避免项目演变为只有数据库 CRUD 的后台系统，或者以商品搜索为主的购物机器人。

## 4. 已完成阶段：衣橱驱动的穿搭 MVP

### 4.1 阶段目标

让 Agent 能读取当前用户的真实衣橱，并优先使用已有衣物生成一套完整 Outfit。

本阶段完成后，项目应第一次形成真正符合产品定位的纵向业务闭环：

```text
用户提出穿搭需求
→ Agent 查询该用户的可用衣物
→ Agent 检索相关服装知识
→ Agent 生成基于已有衣物的 Outfit
→ Agent 说明搭配理由和衣橱缺口
```

### 4.2 实施顺序

1. [已完成] 创建当前用户衣橱查询能力。
2. [已完成] 将衣橱查询封装为 Agent Tool。
3. [已完成] 在请求级数据库 Session 中创建衣橱 Tool。
4. [已完成] 将请求级 Tool 安全地注入 LangGraph，避免缓存数据库 Session。
5. [已完成] 让 Agent 优先根据查询到的衣物生成 Outfit。
6. [已完成] 为 Outfit 回复定义稳定的结构。
7. [已完成] 增加 Tool、Graph、API 和真实数据库链路测试。

### 4.3 Outfit 最小输出

一份 Outfit 应尽量包含：

- 搭配名称
- 适用场景
- 上装
- 下装
- 鞋履
- 按需提供的外套和配饰
- 搭配理由
- 颜色和面料关系
- 已使用的衣橱单品
- 可替换单品
- 衣橱缺口

不能为了填满结构而虚构用户拥有的衣物。

### 4.4 衣物状态决策

当前只保留两种业务状态：

- `available`：当前可以参与穿搭推荐
- `unavailable`：当前不参与穿搭推荐

待洗、清洗中、晾晒中或暂时找不到，对当前推荐结果的影响相同，因此现阶段不拆分成多个状态。

如果以后确实需要洗衣提醒，可以在不改变可用性判断的前提下增加不可用原因。

### 4.5 阶段验收标准

1. Agent 只能读取当前用户的衣橱。
2. 用户 ID 不能由 LLM 或请求正文指定。
3. 不可用衣物不能进入推荐候选。
4. 有合适衣物时优先使用已有衣物。
5. 没有合适衣物时如实说明缺口，不虚构衣物。
6. 未获得用户购物意愿时，不自动搜索商品。
7. 单元测试和集成测试通过。

### 5.4 后续里程碑：上下文、记忆与基础可观测性

上下文、记忆和可观测性解决的是不同问题：

| 能力 | 作用 | 生命周期 |
|---|---|---|
| 上下文 Context | 决定本次模型调用实际看到什么 | 单次模型调用 |
| 短期记忆 | 保留同一会话中的消息和工作流状态 | 一个 `conversation_id` |
| 长期记忆 | 保存跨会话使用的已确认用户事实 | 用户明确修改或删除前 |
| Observability | 让开发者理解请求如何执行及为何失败 | 按日志和追踪策略保留 |

这些能力不能等到项目最后一次性补齐。知识库扩大后，Prompt 长度、来源
冲突和调试难度都会增加，因此应在复杂 Agent 工作流之前建立基础规则。

#### 5.4.1 上下文管理

建立统一的上下文包，明确各部分来源和优先级：

```text
Context Package
├── 当前用户请求
├── 当前轮消息
├── 对话滚动摘要
├── 上一套 Outfit
├── Style Profile
├── 当前轮衣橱和其他工具事实
├── 当前天气
├── 近期 Outfit 与反馈
└── RAG 知识片段
```

上下文优先级：

1. P0：系统规则和当前用户明确要求
2. P1：当前轮工具事实、天气和衣橱
3. P2：Style Profile 和上一套 Outfit
4. P3：对话摘要、近期 Outfit 和历史反馈
5. P4：RAG 参考知识

### 5.5 已完成第一版：结构化需求分析

正式知识库能够提供稳定依据后，为 Agent 增加明确的需求分析结果，例如：

```text
场景：通勤
日期：明天
地点：上海
正式程度：商务休闲
风格：简约
颜色偏好：浅色
衣橱优先：是

信息是否充分：否
```

LangGraph 根据分析结果执行确定性分支：

```text
信息不足
→ 只追问必要问题

信息充分
→ 读取档案、查询衣橱和检索知识

用户明确购物或确认衣橱缺口
→ 才允许查询商品
```

- [已完成] 定义意图、场景、日期、地点、正式程度、风格、颜色、衣橱优先、

## 6. 数据技术的职责

数据库相关计划仍然需要保留，但应围绕业务能力逐步实施。

| 技术 | 主要职责 |
|---|---|
| PostgreSQL | 用户档案、衣橱、Outfit、反馈和外部商品缓存 |

实施原则：

> Agent 当前需要什么数据能力，就优先完善对应的数据接口；不为了表结构完整而提前开发暂时没有消费者的功能。

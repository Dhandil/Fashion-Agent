# Fashion-Agent 开发路线图

## 1. 文档目的

本文档记录 Fashion-Agent 的当前进度、开发顺序、阶段目标和近期任务。

- 产品定位与业务边界以 [产品定位与范围](./product_scope.md) 为准。
- 可测试需求以 [需求规格](./requirements.md) 为准。
- 技术边界和模块职责以 [系统架构](./architecture.md) 为准。

路线图会随着项目推进持续更新，但不得改变以下核心定位：

> Fashion-Agent 是个人穿搭与衣橱助手。它先帮助用户决定怎么穿，再判断是否需要购买。

---

## 2. 产品主线

Fashion-Agent 的核心业务闭环是：

```text
理解用户的穿搭需求
→ 读取用户风格档案和衣橱
→ 排除当前不可用的衣物
→ 结合场景、风格和服装知识
→ 生成完整且可执行的 Outfit
→ 解释搭配理由并允许用户调整
→ 只有缺少关键单品时才建议购物
```

开发工作应优先服务这条主线，避免项目演变为只有数据库 CRUD 的后台系统，或者以商品搜索为主的购物机器人。

## 4. 已完成阶段：衣橱驱动的穿搭 MVP

### 4.1 阶段目标

让 Agent 能读取当前用户的真实衣橱，并优先使用已有衣物生成一套完整 Outfit。

本阶段完成后，项目应第一次形成真正符合产品定位的纵向业务闭环：

```text
用户提出穿搭需求
→ Agent 查询该用户的可用衣物
→ Agent 检索相关服装知识
→ Agent 生成基于已有衣物的 Outfit
→ Agent 说明搭配理由和衣橱缺口
```

### 4.2 实施顺序

1. [已完成] 创建当前用户衣橱查询能力。
2. [已完成] 将衣橱查询封装为 Agent Tool。
3. [已完成] 在请求级数据库 Session 中创建衣橱 Tool。
4. [已完成] 将请求级 Tool 安全地注入 LangGraph，避免缓存数据库 Session。
5. [已完成] 让 Agent 优先根据查询到的衣物生成 Outfit。
6. [已完成] 为 Outfit 回复定义稳定的结构。
7. [已完成] 增加 Tool、Graph、API 和真实数据库链路测试。

### 4.3 Outfit 最小输出

一份 Outfit 应尽量包含：

- 搭配名称
- 适用场景
- 上装
- 下装
- 鞋履
- 按需提供的外套和配饰
- 搭配理由
- 颜色和面料关系
- 已使用的衣橱单品
- 可替换单品
- 衣橱缺口

不能为了填满结构而虚构用户拥有的衣物。

### 4.4 衣物状态决策

当前只保留两种业务状态：

- `available`：当前可以参与穿搭推荐
- `unavailable`：当前不参与穿搭推荐

待洗、清洗中、晾晒中或暂时找不到，对当前推荐结果的影响相同，因此现阶段不拆分成多个状态。

如果以后确实需要洗衣提醒，可以在不改变可用性判断的前提下增加不可用原因。

### 4.5 阶段验收标准

1. Agent 只能读取当前用户的衣橱。
2. 用户 ID 不能由 LLM 或请求正文指定。
3. 不可用衣物不能进入推荐候选。
4. 有合适衣物时优先使用已有衣物。
5. 没有合适衣物时如实说明缺口，不虚构衣物。
6. 未获得用户购物意愿时，不自动搜索商品。
7. 单元测试和集成测试通过。

## 5. 当前及后续阶段

### 5.1 已完成阶段：必要的衣橱与风格管理

目标是补齐 Agent 已经实际需要的数据维护能力，而不是一次开发所有 CRUD。

计划内容：

- [已完成] 查询当前用户衣橱列表
- [已完成] 查看单件衣物
- [已完成] 修改衣物信息
- [已完成] 切换 `available` / `unavailable`
- [已完成] 删除衣物
- [已完成] 创建、查询、完整替换和局部修改用户风格档案
- [已完成] 保存风格、颜色、材质、版型、场景和预算偏好
- [已完成] 区分喜欢与避免的风格和颜色，并校验互斥关系
- [已完成] 由反馈生成偏好候选，并由用户确认后写入长期档案

数据库在该阶段负责保存长期业务事实，但数据库本身不是产品输出。

### 5.2 已完成阶段：Outfit 持久化与个性化

已完成内容：

- 保存用户明确确认的 Agent Outfit
- 查询历史 Outfit
- 收藏和取消收藏
- 用户喜欢、不喜欢和文字反馈
- 根据 Style Profile 和反馈调整后续建议
- 从重复反馈中提取可确认的长期偏好候选

后续仍需补充短期内避免重复推荐同一套衣物的策略。

### 5.3 阶段四：环境与服装知识

计划内容：

- 实时天气
- 温度、降雨和季节约束
- 城市和日期上下文
- 扩充颜色、版型、场景和护理知识
- 根据天气判断 Outfit 是否可执行
- 外部服务不可用时的降级策略

外部天气服务通过 API、Tool 或 MCP 接入，不写入 Agent 核心业务逻辑。

### 5.4 阶段五：辅助购物

购物能力只用于补全衣橱缺口，或者响应用户明确提出的购物需求。

计划内容：

- 衣橱缺口分析
- 购物意愿确认
- 外部商品平台 API 或 MCP
- 商品字段标准化
- 按预算、尺码、颜色和库存过滤
- 商品来源与原始链接
- 推荐前重新确认动态价格和库存

Fashion-Agent 不负责下单、支付、物流和售后。

### 5.5 阶段六：企业级完善

计划内容：

- JWT 或 OAuth 真实身份认证
- Redis Checkpointer 和缓存
- API、PostgreSQL、Redis 的完整 Docker Compose
- MCP Client 和 MCP Server
- 日志、指标和链路追踪
- 限流、超时、重试和熔断
- CI 自动测试和代码质量检查
- 生产环境 Secret 管理

只有单 Agent 工作流稳定后，才评估拆分：

```text
Fashion Supervisor
├── Profile Agent
├── Wardrobe Agent
├── Styling Agent
├── Knowledge Agent
└── Shopping Agent
```

Multi-Agent 是扩展方案，不是当前 MVP 的前置条件。

## 6. 数据技术的职责

数据库相关计划仍然需要保留，但应围绕业务能力逐步实施。

| 技术 | 主要职责 |
|---|---|
| PostgreSQL | 用户档案、衣橱、Outfit、反馈和外部商品缓存 |
| Redis | 短期会话、临时 Agent 状态、缓存和限流 |
| Chroma | 面料、颜色、版型、场景和护理等服装知识 |
| 外部 API/MCP | 实时天气、商品、价格和库存 |

实施原则：

> Agent 当前需要什么数据能力，就优先完善对应的数据接口；不为了表结构完整而提前开发暂时没有消费者的功能。

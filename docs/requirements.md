# Fashion-Agent 需求规格

## 1. 文档目的

本文档将 [产品定位与范围](./product_scope.md) 转换为可开发、可测试和可验收的需求。

当本文档与产品范围发生冲突时，以 `product_scope.md` 中已经确认的产品定位为准。

Fashion-Agent 的核心目标是生成适合用户、符合场景并且能够实际执行的穿搭方案。商品搜索是补全衣橱缺口或响应明确购买需求的辅助能力。

---

## 2. 目标用户

Fashion-Agent 主要服务于希望降低穿搭决策成本、改善个人风格并减少盲目购买的年轻用户。

用户可能具备以下特点：

- 不确定特定场景应该穿什么。
- 拥有一定数量的衣服，但不会组合。
- 对颜色、版型、面料或正式程度缺少判断。
- 希望获得符合预算的建议。
- 希望系统逐渐记住自己的偏好。
- 购买新衣前希望先判断是否真正需要。

---

## 3. 核心用户故事

### US-001：描述穿搭场景

作为用户，我希望用自然语言描述穿搭需求，以便快速获得符合场景的建议。

示例：

> 我明天要参加一个不太正式的面试，天气比较热，应该怎么穿？

Agent 应识别或进一步询问：

- 使用场景
- 日期、季节或天气
- 正式程度
- 风格偏好
- 可用衣物
- 是否接受购买
- 预算（仅在涉及购物时）

验收条件：

1. Agent 能识别用户已经明确提供的信息。
2. Agent 不重复询问用户已经回答的问题。
3. 关键信息不足时，只提出简短且必要的补充问题。
4. 信息足够时，直接进入穿搭方案生成。

### US-002：获得完整穿搭方案

作为用户，我希望得到一套完整、可解释的搭配，而不是零散的服装建议。

穿搭方案应尽量包含：

- 上装
- 下装
- 外套
- 鞋履
- 配饰
- 适用场景
- 推荐理由
- 颜色关系
- 天气或季节注意事项
- 可替换单品

验收条件：

1. 输出结构清晰，用户能够直接照着搭配。
2. 推荐理由与用户场景和约束相关。
3. 不凭空假设用户拥有某件衣物。
4. 存在多种合理选择时，可以提供主方案和备选方案。
5. 近期存在相同 Outfit 时，有合适替代衣物应优先改变至少一件主要单品。
6. 用户明确要求局部调整时，应尽量保留上一套中未要求改变且仍有效的部分。

### US-003：使用用户已有衣橱

作为用户，我希望 Agent 优先使用我已经拥有的衣物，以减少重复和不必要的购买。

验收条件：

1. 用户可以新增、查看、修改和删除衣橱单品。
2. 衣橱单品至少支持名称、品类、颜色、材质、尺码和季节信息。
3. 生成穿搭时，Agent 能区分已有衣物与缺少单品。
4. 存在可用衣物时，不默认推荐购买功能相同的新商品。
5. 用户可以把衣物切换为可用或暂不可用，暂不可用衣物不能参与推荐。
6. 列表、详情、修改和删除只能操作当前用户的衣橱。
7. 衣橱列表支持过滤和分页，并返回相同条件下的总数。

此用户故事属于个人化阶段，不要求在最初的基础聊天版本中一次完成。

### US-004：保存个人穿搭偏好

作为用户，我希望 Agent 记住我的长期偏好，使后续建议更符合我的风格。

偏好示例：

- 喜欢宽松版型
- 常穿黑白灰
- 不喜欢高饱和度颜色
- 不喜欢容易扎肤的面料
- 通勤预算通常不超过 500 元

验收条件：

1. 用户可以主动提供偏好。
2. 用户能够修改或删除已保存的偏好。
3. 后续推荐应考虑仍然有效的偏好。
4. 系统不擅自推断用户未提供的敏感属性。
5. 同一风格或颜色不能同时保存为喜欢和避免。
6. 系统从历史反馈推导出的偏好只能作为候选展示，不能未经用户确认自动写入长期档案。
7. 局部更新只修改用户明确提供的字段，不应清空其他长期偏好。

### US-005：获取服装知识解释

作为用户，我希望了解推荐背后的面料、颜色、版型和护理知识，以便作出自己的判断。

验收条件：

1. Agent 可以使用 RAG 检索服装知识。
2. 知识库信息与用户问题相关。
3. 有来源信息时，API 返回对应来源。
4. 知识库只提供通用知识，不能被当作具体商品数据。
5. 知识库没有答案时，不虚构不存在的专业结论。

### US-006：补全衣橱缺口

作为用户，我希望在现有衣橱无法完成搭配时，知道缺少什么，而不是直接收到大量商品广告。

验收条件：

1. Agent 先说明搭配中缺少的单品及其作用。
2. 用户没有明确购物意图时，先询问是否需要搜索商品。
3. 用户拒绝购买时，优先提供已有衣物的替代方案。
4. 用户同意后，才进入商品搜索流程。

### US-007：搜索真实商品

作为用户，我希望在明确需要购买时获得真实、符合条件的候选商品。

示例：

> 帮我找一条 400 元以内、适合夏季通勤的浅色直筒裤。

验收条件：

1. Agent 调用 `search_products` 或未来的外部商品工具。
2. 商品名称、价格、库存、颜色和尺码以工具结果为准。
3. 支持品类、预算和库存等结构化过滤。
4. 工具返回空列表时，如实说明没有匹配商品。
5. 不使用 RAG 或模型记忆编造具体商品。
6. 正式接入外部平台后，返回商品来源和原始链接。
7. 价格和库存属于动态信息，推荐前应支持重新确认。

### US-008：保持多轮对话上下文

作为用户，我希望在同一会话中继续补充条件，而不必重复所有信息。

验收条件：

1. API 为首次会话生成 `conversation_id`。
2. 相同 `conversation_id` 下能够保留多轮消息。
3. 不同会话之间的短期状态相互隔离。
4. 会话存储不可用时返回明确、结构化的错误。
5. 普通问答不能返回上一轮的旧 Outfit。
6. 最近一次成功生成的结构化 Outfit 可以作为后续局部调整基线。

### US-009：对推荐进行反馈

作为用户，我希望告诉 Agent 哪些建议喜欢或不喜欢，使后续推荐逐渐改善。

验收条件：

1. 用户可以对搭配方案提供喜欢、不喜欢或文字反馈。
2. 反馈与对应用户及搭配方案关联。
3. 用户能够撤销或修改长期偏好。
4. 反馈不能绕过商品真实性、安全和隐私规则。
5. 重复反馈可以形成带证据的偏好候选，但必须由用户明确确认后才能进入长期档案。

此用户故事属于后续个人化阶段。

## 4. 功能需求

### FR-001：需求分析

系统应从自然语言中识别场景、季节、天气、风格、颜色、正式程度、衣橱条件和预算等信息。

### FR-002：补充询问

系统应判断生成可执行方案所需的关键信息是否充分，并避免一次提出过多问题。

### FR-003：穿搭方案生成

系统应生成结构清晰的完整搭配，并解释推荐与用户约束之间的关系。

### FR-004：知识检索

系统应通过 Chroma 检索面料、颜色、版型、季节和护理等非结构化知识。

### FR-005：对话记忆

系统应使用会话 ID 隔离并恢复短期对话状态。

### FR-006：用户穿搭档案

系统应支持持久化用户主动提供的尺码、风格、颜色、材质和预算偏好。

### FR-007：数字衣橱

系统应支持持久化用户已有衣物，提供新增、列表、详情、局部修改、状态
切换和删除能力，并允许按品类和当前可用状态分页查询。所有衣橱操作必须
使用服务端认证身份隔离用户数据。

### FR-008：衣橱缺口判断

系统应区分穿搭方案中已有、可替换和缺少的单品。

### FR-009：商品工具调用

系统只应在用户明确购物或同意补全衣橱缺口时调用商品搜索工具。

### FR-010：商品真实性

系统必须以工具或授权外部数据源提供的结果为具体商品事实来源。

### FR-011：工具注册

Agent 工具应通过 Tool Registry 注册、发现和装配，避免在业务节点中硬编码具体工具实现。

### FR-012：外部能力接入

未来的商品、天气和其他外部服务应通过 API 适配器或 MCP 接入，并与 Agent 核心逻辑隔离。

## 5. 数据需求

### 5.1 PostgreSQL

PostgreSQL 用于保存：

- 用户穿搭档案
- 用户衣橱
- 搭配方案
- 搭配与单品的关系
- 用户反馈与收藏
- 外部商品的规范化缓存

### 5.2 Redis

Redis 用于保存：

- 短期对话状态
- 会话过期时间
- 临时 Agent 状态
- 高频查询缓存
- 限流状态

### 5.3 Chroma

Chroma 用于保存：

- 面料知识
- 颜色搭配知识
- 版型知识
- 穿搭原则
- 季节建议
- 护理知识

### 5.4 外部数据

正式商品、天气等动态数据应来自授权 API、企业内部服务或 MCP Server。

`data/samples` 中的数据只用于开发和测试。

## 6. 非功能需求

### NFR-001：模块边界

API、Agent、领域、工具、RAG、Memory、数据库和外部适配器应保持模块化，领域层不依赖 FastAPI、LangGraph 或具体数据库实现。

### NFR-002：异步 I/O

网络请求、数据库查询和异步工具应使用异步接口，避免阻塞 FastAPI 请求线程。

### NFR-003：配置安全

API Key、数据库密码和 Token 必须通过环境变量或 Secret 管理，不得提交到 Git。

### NFR-004：隐私

系统只收集功能所需的最少用户信息，并为长期资料提供查看、修改和删除能力。

### NFR-005：错误处理

配置、数据库、检索、模型和工具错误应转换为明确的项目异常或结构化 API 响应。

### NFR-006：可测试性

领域规则、仓库、工具、Agent 节点和服务装配应支持 Mock，并具有相应单元或集成测试。

### NFR-007：可观测性

系统应记录结构化日志、请求标识、关键工具调用和错误信息，但不得在日志中暴露密钥或完整敏感数据。

### NFR-008：可部署性

项目应支持通过 Docker Compose 启动 API、PostgreSQL、Redis 和其他必要服务。

### NFR-009：可扩展性

单 Agent 工作流稳定后，应能够在不改变 API 和核心领域边界的情况下扩展 MCP 与 Multi-Agent。

## 7. MVP 范围

### 7.1 当前 P0

- FastAPI 聊天接口
- 基础 LangGraph 工作流
- DeepSeek/OpenAI 兼容模型
- 多轮短期对话
- 服装知识 RAG
- 通用穿搭建议
- Tool Registry
- 样例商品搜索
- 商品真实性提示规则
- 统一配置和异常处理
- 用户穿搭档案
- 数字衣橱及管理接口
- 基于已有衣物生成结构化 Outfit
- 衣橱缺口判断
- Outfit 保存、查询、收藏和反馈
- 根据长期档案和反馈进行个性化
- PostgreSQL 持久化和 Alembic 迁移

### 7.2 下一阶段

- 减少短期内重复 Outfit
- Outfit 局部调整
- 实时天气和环境约束
- Redis 会话存储

### 7.3 暂不包含

- 自动下单和支付
- 物流和售后
- 自营商城
- 未授权商品抓取
- 复杂虚拟试衣
- 时尚社区
- 服装生产或设计系统

---

## 8. MVP 完成标准

一个版本只有同时满足以下条件，才可以认为完成相应需求：

1. 代码遵循项目模块边界。
2. 关键变量、函数和公共接口具有清晰说明。
3. 单元测试通过。
4. 相关集成测试通过。
5. Ruff 和 Mypy 不存在阻断性错误。
6. 不提交 `.env`、数据库数据、模型缓存或真实密钥。
7. 文档与实际行为保持一致。
8. 新能力不会破坏已经通过的 Agent、RAG 和 Tool 链路。

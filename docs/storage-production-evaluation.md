# 生产对象存储评估与迁移边界

## 1. 当前结论

当前本地文件卷方案继续保留，不新增 MinIO、S3 SDK 或云存储依赖。它适合个人
开发、单机 Docker 和本地演示；生产环境再替换为实现同一协议的 S3-compatible
Provider。

原因是图片业务边界已经由 `WardrobeImageStorage` 和
`wardrobe_image_assets` 元数据表固定下来，现在提前引入新的存储服务只会增加
部署和凭证管理成本。

## 2. 方案比较

| 方案 | 当前适用性 | 优点 | 主要代价 |
|---|---|---|---|
| 本地文件卷 | 本地开发、单机演示 | 零新增服务、调试简单 | 无跨主机高可用和备份能力 |
| MinIO | 私有化部署或离线测试 | S3 兼容、可自托管 | 需要额外容器、磁盘和运维 |
| 云对象存储 | 生产部署 | 持久化、权限、生命周期和扩展能力成熟 | 产生存储/流量费用，需要云凭证 |

生产默认建议使用云对象存储；只有明确需要本地化或离线环境时再部署 MinIO。

## 3. Provider 迁移约束

生产 Provider 必须继续实现以下能力，不允许业务路由直接依赖 SDK：

- `write(object_key, content)`：服务端回退上传或异步复制；
- `read(object_key)`：内部识别读取，不能暴露公开路径；
- `exists(object_key)`：上传完成校验；
- `delete(object_key)`：清理任务幂等删除。

S3/MinIO 版本还需要增加独立的 presigned PUT/GET 适配能力，但 `image_asset_id`、
用户隔离、SHA-256、状态机和清理服务保持不变。

## 4. 迁移顺序

1. 增加 S3-compatible Provider 和单元测试，不改变本地 Provider 默认值；
2. 在测试 Bucket 完成上传、读取、用户隔离、失败重试和删除生命周期验证；
3. 将 Docker/生产环境通过配置切换 Provider，禁止把 Bucket 密钥写入镜像；
4. 对历史本地资产执行一次可审计迁移，校验 SHA-256 后再切换 `object_key`；
5. 观察稳定运行后，才考虑停止旧的永久 `image_url` 兼容写入。

## 5. 暂不做的事情

- 不在本地开发阶段强制启动 MinIO；
- 不在没有生产 Bucket 和凭证前新增云 SDK 依赖；
- 不把签名 URL 写入长期衣橱记录；
- 不改变衣橱、商品、天气和 Memory 的数据边界。
